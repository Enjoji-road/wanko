## 1. 実装した全体構造

1. 通常プレイを60秒・誤答・蓋のいずれかで終了する。得点と自己ベストは従来の結果画面に表示する。
2. 従来と同じ待ち時間の後、お給仕さんが「あっ、まだ一杯ありますよ？」と誘う。プレイヤー自身が入口のボタンを押す。
3. 「まだ食べていない一杯は、どれ？」と、底まで見える空の椀4つを表示。どれを選んでも「そちらは、もう空ですよ？」となり、そのまま観察を続けられる。
4. 同じ画面で、入口にあった五段のお椀とお給仕さんを見直す。タイマーはなく、誤答によるドボンもない。
5. 食べた順番へ視点を変え、五つの印を下から上へ読む。
6. お給仕さんの手元を拡大し、読んだお願いを伝える。お願いが通ると、プレイヤー自身が「蓋を取る」を押せる。
7. 同じお椀の蓋が外れ、中にあったそばが見える。「見つかっちゃいましたね！」「最後の一杯は、最初からここにあったんですよ。」で特別なクリアへ。
8. 通常の記録画面へ戻る、同じ入口へ戻る、この一杯だけやり直す、の三つを用意。通常の杯数は増やさない。

## 2. 最初から観察できる手掛かり

| 手掛かり | 通常時 | 特別な一杯での意味 |
| --- | --- | --- |
| 五段のお椀の印 | 入口の既存の装飾へ、上から「れ・と・を・た・ふ」を追加 | 食べ終えた順に読む指示 |
| お椀を上へ重ねる | 入口の遊び方に一行を追加。実際の得点の山も、従来から新しい椀を上へ重ねる | 最初の一杯は一番下だと判断できる |
| お給仕さんの蓋付きの椀 | 既存のSVGには蓋がなかったため、同じ椀へ蓋を新規に描き足した。入口・通常プレイ・結果すべてで同じ素材を使う | 空の四つ以外に残っていた一杯 |
| 四つの椀の内側 | 特別な一杯で最初から底と内側の輪郭が見える | 四択の内側だけで探す必要はない |
| 「最初の一杯を、覚えていますか？」 | 特別な一杯でお給仕さんが言う | 最初の画面と、積む順番の両方を考え直す |

五段のお椀と入口のお給仕さんは、特別な一杯で別の絵を複製するのではなく、**入口の同じDOM要素を移動**して使う。戻ると元の場所に戻す。特別な一杯の開始を条件に文字を追加・変更する処理はない。通常の開始前から文字を読んでもよい。

これらの印・蓋・一行の説明は今回新しく追加する伏線であり、以前の45問版に実装されていた情報ではない。

## 3. 想定するひらめき

最初はいつもの四択だと思う。ところが四つとも空で、誤っても終わらない。底が見える絵とお給仕さんの反応が一致しているので、選択肢の当て直しよりも、ほかに一杯がないかを観察する理由が生まれる。

五段のお椀では、上から読むと「れとをたふ」。単なる逆読みの記号はないが、普通のプレイでお椀を上へ積んだことと、入口の説明が読む方向の根拠になる。最初の椀＝最下段と捉えると「ふたをとれ」になり、空の椀にはない蓋を探す意味が生まれる。

先にお給仕さんの蓋へ気づいてもよい。拡大だけではクリアにならず、「何をお願いするか」を考える段階が残る。印を先に読む場合も、四つの空の椀を先に調べる場合も、同じ短いお願いと蓋の操作へ収束する。

「空の椀を全て選択済み」「ヒントを全て表示済み」といった履歴は条件にしていない。意味に気づいた人は直ちにお願いできる。

## 4. 当初案からの変更と比較

| 候補 | 長所 | 弱点・判断 |
| --- | --- | --- |
| お給仕さんの椀を一回タップ | 直感的で操作が少ない | 無関係なタップで即終了するため不採用 |
| 蓋を上へドラッグ | 「取る」が身体的な操作になる | 手元の少数の対象を触るだけで偶然開きやすく、ドラッグが難しい人への代替も必要。今回は不採用 |
| 五文字を順番にタップしてから開く | キーボードが不要 | 印を押した履歴を要求することになりやすく、120通りの順番試しにもなる。今回は不採用 |
| **読んだお願いを伝え、蓋を取る** | 四択や無関係なタップでは終わらず、読んだ意味がそのまま操作になる。押す履歴の条件がない | **採用**。短い文字入力が一回必要で、お願いを推測する近道は残る |
| 語句を長くする・追加暗号を課す | 文字列の偶然一致は減る | 主役の認識転換より入力や暗号が重くなるため不採用 |

採用案は「最後の一杯を選ぶ」から「蓋を取って一杯を現す」へ、行動の意味を変える。追加の大きな暗号は設けない。通常終了の「蓋をする」と最後の「蓋を取る」が反対になる点を利用した。今回、通常の終了ボタンを裏で別の操作へ流用することはしていない。

## 5. 偶然と総当たりの確認範囲

- 空の4択、ヒント、手元の拡大だけでは状態が成功へ移らない。四択の全組合せを選び続けても正解はない。
- お椀の印から作れる5!＝120通りの文字列のうち、採用する指示は1通り。これは出題データの整合性確認であり、120通りあれば総当たりに強いという主張ではない。
- 類似のお願いを自然に受け付ける。「フタヲトレ」「蓋を取れ」「蓋を取って下さい」「ふたを取ってもらえますか」などを正規化・許容する。部分一致や一文字ずつの正解表示はしない。
- 正しいお願いを入力した後も、自動ではクリアせず「蓋を取る」を本人が操作する。
- 試行回数制限、待ち時間の罰、必須クリック履歴、必要ヒント数はない。
- **「蓋を取って」と観察だけから推測して入力する近道は残る。印を読んだと証明することはできない。**静的なクライアントゲームなのでソース閲覧による回避も防げない。防げたのは空の四択の総当たりと偶然の単発タップであり、謎の理解そのものを技術で保証したものではない。

## 6. 状態と通常ゲームの保護

| 状態 | 操作 | 結果 |
| --- | --- | --- |
| question | 空の椀、拡大、ヒント、不正なお願い | 続けて観察できる。得点や終了への遷移なし |
| question | 指示をお願いする | ready |
| ready | 蓋を取る | revealed。特別な発見を保存 |
| ready | 中断して記録画面へ | 準備状態を同じページ内で保持 |
| revealed | 空の椀や蓋の再操作 | 二重加点や二重終了はない |
| revealed | この一杯をやり直す | question。過去の発見記録は保持 |

通常の`app.js`・`model.js`・`config.js`・45問の`questions.js`・描画`puzzle-view.js`・基本CSS類は45問版とバイト単位で一致する。SHA-256を`tests/last-bowl-protected.json`へ保存し、テストで照合する。

変更した通常画面は、入口の文字付き五段と配置、素材の蓋、積む順番の説明、結果の特別な一杯の入口、追加モジュールの読み込みである。新しいCSSは別ファイルとし、通常プレイの問題・選択肢・時計の配置を変更しない。

保存キーは予約済みだった`wanko-extra-bowl-v1`だけを使用し、`{version:1,cleared:true}`を保存する。入力したお願い自体は保存しない。通常の`wanko-choice-suddendeath-records-v1`や以前の入力式の記録には書き込まない。ネットワーク送信もない。

再読み込みでは普通の入口を表示し、特別な一杯を自動開始しない。通常プレイ終了後、本人が「もう一度見る」を選んだ場合だけ保存済みの発見を再表示する。未クリアの途中状態は同じページ内で保持し、再読み込みすると最初からになる。これは今回の試作の仕様とする。

## 7. 検証結果

### 独立したコード

- `node tests/verify.cjs`：43,021チェック成功。通常45問、全180選択、600回のシャッフル、60秒の期限、パス・蓋・記録の既存検証を維持。
- `node tests/verify-extra-bowl.cjs`：4,207チェック成功。4,096通りの空選択6回＋蓋、印120順列、状態遷移、表記ゆれ、保存破損・不可、通常8ファイルの未変更を検証。
- 蓋を描いたSVGから新規の蓋グループを除くと、開いたSVGと一致する。同じお給仕さん・同じお椀であり、クリア時に別の食器を生成しない。

### 実ブラウザ

Cloud Chromiumと開発用のiframeで確認。実機iPhone/Safariでの確認とは区別する。

| 項目 | 結果 |
| --- | --- |
| 通常の正解・即次問、誤答ドボン、蓋2回、時間切れ | 正常 |
| 三つの終了理由から特別な一杯へ | 入れる |
| 空の四つを全て選ぶ | ドボンせず続行、クリアもしない |
| 不正なお願い、日本語変換中のEnter | 誤クリアせず、変換中は送信しない |
| 正規のお願い＋蓋操作 | 最後の一杯が現れ、クリアになる |
| ヒントや空選択を使わず指示が分かる場合 | そのまま解ける |
| 通常記録との分離 | 特別な一杯の前後で通常記録の文字列が同一 |
| 中断・再開、クリア後の入口へ復帰 | できる |
| 再読み込み | 通常の入口。通常ベストと特別な発見を保持。勝手な特別クリア再生なし |
| 保存不可 | 両方とも遊べる。発見保存の失敗を表示 |
| 動きを減らす設定の模擬 | 静止した状態で観察・蓋・クリアが成立 |
| クリア後のフォーカス | クリア見出しへ移り、メッセージが見える |

全45問を320×568・390×660・844×390・1280×900の4サイズで一巡し、180表示で問題・選択肢の重なりと横はみ出しなし。縦2サイズは正解、横向きとPCはパスの実ボタンのハンドラを検証ページから動かした。180回を人間が初見で解いたという意味ではない。

入口と特別な一杯も同じ4サイズで測定。印は上から「れとをたふ」で、文字のCSSサイズはスマホ18px、PC19px。縮小によって文字だけが極小になる処理を外した。当初のスマホ表示で最下段がスタートボタンに隠れる問題が見つかったため、入口をグリッド配置に直した。結果画面の新しい誘い文も、320px幅で改行しない指定による11pxの横はみ出しを見つけて修正し、横幅305pxに対してscrollWidthも305pxになることを再確認した。時間制限のない特別な一杯では、低い画面は縦スクロールを許容する。手元のダイアログも縦にスクロールできる。

詳細な実測値は`tests/last-bowl-browser-evidence.json`。段階的ヒント、変換中Enter、保存不可、動きを減らす設定は開発用ハーネスから条件を模擬したものを含む。iOSのソフトウェアキーボードの実際の挙動、スクリーンリーダーの読み上げ、初見の楽しさは未検証。

## 9. 現段階の最大の弱点

逆順で一度読むだけなので、ひらめきは軽い。「四択の外へ目を向ける」「装飾を読む対象へ変える」「蓋をするから取るへ変える」の重なりが、初見で十分な達成感になるかは未確認である。

また、初期画面の印は公平性のため読める大きさにした。その分、慣れたプレイヤーには最初から暗号だと分かる可能性がある。隠し謎を知っている作者の目視だけで、自然な装飾だと断定できない。

お願い入力は偶然のタップ対策になるが、物理的な蓋を見ただけで同じお願いを思いつく人もいる。近道を塞ぐために指示を不自然な長文へ変えたり、印のタップ履歴を必須にしたりする方が体験を損ねると判断した。採用は仮であり、初見結果が弱ければ見直す。

## 10. 次の試遊で決めたい改善

1. 5〜8人程度へ、隠し謎の解法を伝えず通常プレイから遊んでもらう。気づく時点・視線・最初のお願い・ヒント回数を人が観察する。今回、オンライン収集機能は入れない。
2. 印が最初から謎に見えるなら、文字を小さくするのでなく、印の周囲に既存の店の意匠と一体になる細い金の枠などを試す。視認性は維持する。
3. 「ふたをとれ」がそのまま推測されるなら、まずはお願い入力と直接的な蓋ドラッグの二版を比べる。近道を許しても発見が気持ちよい方を採る余地がある。
4. 読むだけで終わった印象が強い場合は、普通の終了で閉じた椀と、お給仕さんが保持していた椀の対比を強める。ただし通常終了の操作と記録は変更しない。
5. 「最初の一杯」が最初の小謎と混同されて長く迷う場合、段階ヒントの2番目を出すタイミングや言葉を比較する。最初から読む方向まで説明するのは避ける。
6. スマホでお願い入力のキーボードが負担なら、外部IMEを使わない代替を研究する。ただし五文字タップを必須履歴へ戻したり、選択肢に正解文を直接出したりしない。

## 試遊と再検証

`dist/index.html`を開き、通常プレイを一度終了してから結果の誘いを選ぶ。ローカルファイルの保存制限がある場合は、`dist/`をローカルHTTPサーバーで開く。公開版にはまだ反映されていない。

```sh
node tests/verify.cjs
node tests/verify-extra-bowl.cjs
```

開発用の表示検証は`tests/last-bowl-fixture.html`を一時的に`dist/qa.html`へコピーして使う。記録初期化は検証オリジンの特別な一杯の試験記録だけを対象にする。公開版やプレイヤーの記録に対して実行しない。
