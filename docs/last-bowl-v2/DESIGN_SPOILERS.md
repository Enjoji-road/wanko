# 「最後の一杯」第2次試作 設計・検証報告

> **この資料には解法がすべて書かれています。**  
> 作成日：2026-11-03。これは完成仕様ではなく、初見試遊のための比較用試作である。

## 1. 実装した全体構造

1. 通常ゲームは従来どおり、時間切れ・誤答・蓋のいずれかで結果画面へ進む。
2. 結果画面で「あっ、まだ一杯ありますよ？」から、時間制限のない特別な一杯へ入る。
3. 「まだ食べていない一杯は、どれ？」に対して、底まで見える空の椀を四つ提示する。どれを選んでもドボンにならず、四つとも空だと観測できる。
4. 入口から存在する五段の椀には、上から「に・か・な・の・て」の印がある。通常プレイで椀を上へ積んだ経験と、入口の「食べ終えたお椀は、上へ重ねて」を根拠に食べた順、つまり下から読むと「てのなかに」になる。
5. 特別画面でも、入口と同じ店先DOMを移動して表示する。印やお給仕さんを後から複製・追加しない。
6. 読んだ場所、または画面観察から、お給仕さんが最初から手にしていた蓋付きの椀へ気づく。
7. 画面上のその椀を直接タップすると手元が拡大される。拡大された椀全体が操作領域で、タップ・Enter・Spaceで蓋を取れる。
8. 蓋の下には元のSVGに描かれていたそばが現れ、「最後の一杯は、最初からここにあった」と分かる。通常の杯数とは別のキーへ発見記録だけを保存する。

## 2. 第1次試作から変えたもの

| 項目 | 第1次 | 第2次 |
| --- | --- | --- |
| 五段の印 | 上から「れとをたふ」、下から「ふたをとれ」 | 上から「にかなのて」、下から「てのなかに」 |
| 最終回答 | お願いを文字入力し、その後に蓋を取る | 手元の椀を直接調べ、拡大した蓋を直接開く |
| キーボード | 日本語IMEを使用 | 入力欄なし。Tab＋Enter／Spaceで対象を操作 |
| 初期誘導 | 「店の中を見渡して」「手元を見る」ボタン | どちらも撤去。店先の実物が操作対象 |
| 偶然対策 | 正しいお願い文を要求 | 手元を発見するタップと、拡大後の蓋操作を分離 |
| ヒント | 最後にお願いを伝えるよう指示 | 最後に場所を示す五文字だと伝え、実物の椀だけを強調 |

文字入力が謎の理解を証明する関門になっていた一方、通常ゲームの4択・直接操作という方針から外れ、スマートフォンではIMEが画面を覆っていた。第2次では理解履歴を隠し条件にせず、見つけた対象をそのまま操作する。

## 3. プレイヤーに見える手掛かり

- 通常開始時から、五段の椀と五つの印が読める。
- 同じ開始画面で「食べ終えたお椀は、上へ重ねて」と説明される。
- 通常プレイでは、正解のたびに完食椀が上へ積み上がる。
- お給仕さんは、入口・プレイ中・結果・特別画面を通して蓋付きの椀を持つ。
- 特別画面の四つの椀は、どれも底まで描かれた空の椀である。
- 四つすべてを確認すると「この四つの中にはない」と明記し、お給仕さんが「最初の一杯を、覚えていますか？」と返す。
- 手元の椀は初期状態で輪郭を光らせない。キーボードでフォーカスした時は通常のフォーカス枠を出す。
- 最終段階ヒントまで見た場合だけ、手元の椀の周囲へ明確な輪を表示する。

## 4. 想定する思考の流れ

### 主経路

1. いつもの4択だと思い、椀を一つ選ぶ。
2. 空だと返され、ほかの三つも同じだと気づく。
3. 四つを調べても失敗にならず、「四つの外」を探す問題だと捉え直す。
4. 特別画面にも入口と同じ五段の椀があることに気づく。
5. 最初に食べた椀は最下段なので、下から「てのなかに」と読む。
6. お給仕さんの手元を見ると、最初から蓋付きの椀を持っている。
7. 椀を調べ、拡大した蓋を開く。

### 観察による短経路

最初からお給仕さんの蓋付き椀へ気づき、直接調べても正解とする。暗号を読んだ履歴や空の四つを押した履歴は要求しない。ゲーム画面の観察から対象を特定したなら正当な発見である。

## 5. 操作性の改善

- 日本語入力欄、送信ボタン、表記ゆれ正規化、IME制御をすべて削除した。
- 特別画面上の椀の操作領域は、PCで92×78px、320/390px幅で82×72px。実際の絵の椀中心を領域内に収めた。
- 拡大後は小さな蓋だけでなく、216×190px（スマホは216×170px）の椀画像全体を押せる。
- どちらもネイティブの button で、Tab移動とEnter／Spaceに対応する。可視フォーカスを出す。
- クリア時はダイアログを閉じ、クリア見出しへフォーカスを移して表示位置を合わせる。
- prefers-reduced-motion では蓋の移動を省き、同じ観測結果を即座に表示する。
- 320pxと390pxの低い縦画面では特別画面を縦スクロールできる。手元の対象は画面幅からはみ出さない。

## 6. 公平性・伏線・偶然クリアの評価

### 検証できたこと

- 文字は隠し謎開始時に生成されず、通常開始時から同じ五段へ存在する。
- 特別画面はその店先DOM自体を移動する。見た目が似た別物ではない。
- 上へ積む説明、通常プレイの積み上がり、最下段を起点にするヒントが読み方向の根拠になる。
- 四つの空椀、ヒント、画面の観察だけではクリアしない。実物の手元を調べ、拡大した椀をもう一度操作した時だけクリアする。
- 正解履歴を要求する隠しフラグはない。暗号を読まない観察解も成立する。

### 検証できないこと

- 「最初からそこにあった」という驚きが十分かは、実装者の確認では判断できない。
- 視線が自然に五段へ戻るか、暗号を読む前に手元を偶然タップする割合は、初見試遊が必要である。
- 画面内を手当たり次第に連打すれば、手元の領域と拡大した椀の二回が偶然つながる可能性は残る。これを塞ぐための読字履歴や操作順は入れていない。

単発タップ一回ではクリアせず、最初は手元の拡大だけが起きる。次に蓋付きの椀を本人が操作するため、偶然性は第1次より増えたものの、無関係な一回のタップによる即クリアは避けている。

## 7. 「てのなかに」の評価

五文字が操作命令ではなく場所を示すため、認識転換の中心を「指示どおり蓋を取る」から「誰の手にあるのか見直す」へ移せた。画面には手で椀を持つ人物が一人しかおらず、候補は絞れる。

一方、絵では椀が厳密には「手の中」より「手の上」にあるため、言葉の自然さには小さなずれがある。また、スマホでは店先の下部まで少しスクロールしないと手元が見えない。初見で「自分の手」「端末を持つ手」を連想して止まる場合は、次の比較候補を試す。

| 候補 | 長所 | 問題 |
| --- | --- | --- |
| てのなかに | 今回採用。五文字で人物へ視線を移せる | 絵は手の上。所有者が省略される |
| てにあるよ | 位置関係が絵に近い | 説明口調で、発見の余韻が弱い |
| てにもつ（四文字） | お給仕さんの動作に直結 | 五段を使い切れない |
| おぼんのうえ（六文字） | 位置が明確 | 現在の五段では置けない。答えを限定しすぎる |

現段階では指定どおり「てのなかに」を仮採用し、初見の発話と停止点を比較する。

## 8. 状態と保存

状態は特別な一杯だけの question と revealed の二つである。

| 状態 | 操作 | 結果 |
| --- | --- | --- |
| question | 空椀、ヒント、手元の拡大 | questionのまま |
| question | 拡大した蓋を開く | revealed。特別記録を保存 |
| revealed | 再挑戦 | question。過去の発見記録は保持 |

保存キーは第1次と同じ予約済みの wanko-extra-bowl-v1 だけを使い、{version:1,cleared:true} を保存する。通常記録 wanko-choice-suddendeath-records-v1、杯数、自己ベスト、出題履歴へ書き込まない。保存不可でもクリアでき、保存できなかった旨だけを表示する。

- dist/extra-bowl-model.js：二状態の独立モデルと印。
- dist/extra-bowl.css：実物に重なる操作領域、拡大した椀全体の操作、最終ヒントの強調。

## 10. 実施した検証

### 自動検証

- node tests/verify.cjs：43,021チェック成功。通常45問、180選択、600回シャッフル、60秒、即ドボン、通常保存を再確認。
- node tests/verify-extra-bowl.cjs：4,142チェック成功。通常8ファイルのSHA-256一致、五印の物理順、4,096通りの空椀操作列、直接蓋操作、独立保存、保存破損・不可を確認。
- HTMLとコントローラに requestInput、requestForm、お願い入力文、REQUESTイベントが残っていないことを検査。

### Cloud Chromium

- PC 1363×936、スマホ相当320×568・390×660で通し操作。
- 320pxと390pxで横はみ出しなし。手元の実物領域は82×72px、拡大後の椀は216×170px。
- 実物領域の中心とSVG内の椀中心は、320pxと390pxで数pxの差に収まった。
- 四つの空椀をすべて押しても未クリア。最終ヒント後だけ手元へ強調輪が出る。
- 手元をタップ→ダイアログ→拡大した蓋をEnterで開く→クリア見出しへフォーカス、を確認。
- 通常記録 {"version":1,"bests":{"60":0}} と特別記録 {"version":1,"cleared":true} が別に保存された。
- 再読込では入口に戻り、通常終了後の明示的な入口からだけ発見済み画面へ入る。再挑戦で暗号画面へ戻れる。
- 動きを減らす模擬条件では待ち時間なしでクリアを認識できた。
- localStorageを拒否する模擬条件でもクリアでき、保存不可表示を確認した。

詳細値は tests/last-bowl-v2-browser-evidence.json に記録した。実機iPhone/Safari、実際のタッチ誤差、スクリーンリーダーは未検証である。

## 11. 現段階の問題点

1. 手元の椀は通常から目立つため、観察力の高い人は五段を読まずに解ける。今回は正当な別経路として許容しているが、伏線の印象が薄くなる割合は未測定。
2. 「てのなかに」の日本語と、手の上に載った絵のずれは初見確認が必要。
3. 320px×568pxでは四択とお給仕さんを同時には見切れず、縦スクロールが必要。時間制限はないが、画面外へ視線を移す意図が伝わるかは未確認。
4. 表示上は透明な操作領域なので、画面を全面連打する人の偶然クリアは理論上残る。
5. 作者・実装者による操作確認は、驚き・納得感・平均ヒント数を証明しない。

## 12. 次回試作で比較すること

1. 5〜8人へ解法を伏せ、通常ゲームから遊んでもらう。最初の空椀、五段、手元のどこを最初に見るか、ヒント回数、発話を記録する。
2. 「てのなかに」と「てにあるよ」の二版を、同じUIで比較する。
3. 手元直行が多すぎる場合、通常時の蓋を隠すのではなく、四つの空椀を調べた後だけ台詞を「最初の一杯を覚えていますか？」へ変える現仕様が十分か確認する。
4. 手元を発見できない人が多い場合、ヒント3で五段だけ、ヒント4で手元だけを強調する現在の段階を維持し、初期の透明領域は目立たせない。
5. 実機iPhone/Safariで、320px相当のスクロール、タップ領域、ダイアログ、戻る操作を確認する。

初見で驚きが弱ければ、暗号を複雑にする前に、通常プレイ中に同じ蓋付き椀を何度見るかと、結果画面から特別画面への間の取り方を調整する。中心は暗号の難度ではなく、見慣れたお給仕さんの意味が変わる瞬間である。
